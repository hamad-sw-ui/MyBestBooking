## A1 — Messages d'erreur zod en anglais exposés au client (i18n/UX)

**Problème.** Beaucoup de schémas de validation des routes grand public
n'attachent pas de message explicite à leurs contraintes. Zod renvoie alors ses
libellés par défaut **en anglais**, qui étaient renvoyés tels quels via
`error.issues[0].message` jusqu'au navigateur :

- `POST /api/bookings` avec `numAdults: 0` → `400 "Too small: expected number to be >=1"`
- `POST /api/bookings` avec `guestEmail: "pasunemail"` → `400 "Invalid email address"`
- `POST /api/reviews` avec `overallRating: 99` → `400 "Too big: expected number to be <=10"`
- `POST /api/price-alerts` avec `maxPrice: -5` → `400 "Too small: expected number to be >0"`

C'est en contradiction avec une interface 100 % française et le travail i18n
T-134. (D'autres routes admin/hôte ont le même travers mais ne sont pas
exposées au grand public ; le helper est disponible pour les corriger plus tard
sans effort.)

**Solution.**
- Nouveau helper `frenchZodMessage(error)` dans `src/lib/http.ts` :
  - préserve **tout message personnalisé déjà rédigé en français** (il ne
    remplace que les libellés zod par défaut détectés comme anglais) ;
  - traduit les codes natifs Zod (v4) : `too_small`/`too_big` (numérique →
    « Valeur trop petite/grande » ; texte → « trop court/long »),
    `invalid_format` / `invalid_string` (email → « Adresse email invalide »,
    uuid → « Identifiant invalide », sinon « Format invalide »),
    `invalid_type` (email → « Adresse email invalide », sinon « Valeur invalide
    ou manquante »).
- Appliqué aux points d'entrée client : `api/bookings/route.ts`,
  `api/bookings/[id]/route.ts`, `api/reviews/route.ts` (2 blocs),
  `api/price-alerts/route.ts`.
- Tests unitaires : `src/lib/http.test.ts` (+5 cas, dont « le message
  personnalisé français est conservé »).

**Sans régression :** les messages personnalisés (ex. « Le mot de passe doit
contenir au moins 8 caractères ») restent intacts ; seuls les libellés anglais
par défaut changent. Le code de statut reste 400.

**Preuve runtime (DEV).**
- réservation `numAdults=0` → `400 "Valeur trop petite"`
- réservation `guestEmail` invalide → `400 "Adresse email invalide"`
- avis `overallRating=99` → `400 "Valeur trop grande"`
- alerte prix `maxPrice=-5` → `400 "Valeur trop petite"`

## A2 — Parcours de modération propriété en impasse (rejet/suspension non re-soumissibles)

**Problème.** Quand un administrateur **rejette** une annonce, son statut
passe à `draft` ; quand il la **suspend**, à `suspended`. Or :
- le changement de statut générique (`PUT /api/properties/[id]`) est réservé à
  l'admin — un hôte reçoit `403 « Modification du statut réservée à
  l'administration »` ;
- la page d'édition hôte n'envoie **aucun champ `status`** et n'offre **aucun
  bouton d'action** ;
- le badge affichait le statut brut (`draft`, `suspended`) en anglais/technique.

Résultat : une annonce rejetée ou suspendue restait **bloquée indéfiniment et
invisible du public**, sans recours pour l'hôte. Le parcours de modération
était cassé en boucle (la route de rejet précise pourtant dans son commentaire
« reject → status='draft' (l'hôte peut re-soumettre) », mais le moyen de
re-soumettre n'existait pas).

**Solution.**
- Nouvelle route `POST /api/properties/[id]/submit` :
  - autorisée au **propriétaire** de l'annonce ou à un admin ;
  - fait passer `draft` ou `suspended` → `pending` (re-soumission) ;
  - `pending` → réponse idempotente (déjà en attente) ;
  - `active` → `409 « Cet hébergement est déjà actif »` ;
  - autres états (`archived`) → `409` ;
  - **l'hôte ne peut jamais atteindre `active`** : la publication reste
    exclusivement du ressort de l'admin via `/validate` (approve) ; les
    garde-fous existants (PUT statut → 403) sont inchangés.
- Nouveau composant `src/components/property-submit-button.tsx` (« Soumettre
  pour validation »), affiché uniquement en états `draft`/`suspended`.
- Page d'édition `dashboard/properties/[id]/page.tsx` : bouton ajouté dans
  l'en-tête, bannière ambrée explicative, et badge de statut **en français**
  (« Brouillon / rejeté », « Suspendu », « En attente de validation », « Actif »).

**Sans régression :** aucune route existante n'est modifiée dans son contrat ;
l'auto-approbation reste impossible (vérifié : hôte `PUT status=active` → 403).

**Preuve runtime (DEV), cycle complet :**
- admin `reject` → 200 (statut `draft`) ;
- hôte `POST .../submit` → 200, statut `pending` ;
- hôte `PUT status=active` → **403** (pas d'auto-approbation) ;
- utilisateur tiers (non propriétaire) `POST .../submit` → **403** ;
- admin `approve` → 200, statut final `active` (remise en état) ;
- hôte sur propriété déjà `active` → **409 « déjà actif »** ;
- anonyme → **401**, id inexistant → **404**.

## A3 — Aucun renvoi possible de l'email de vérification

**Problème.** À l'inscription le compte est créé avec `emailVerified=false` et
un premier email de vérification est envoyé (T-013). Mais :
- il n'existait **aucun endpoint ni bouton pour renvoyer** cet email ; si le
  lien expirait (TTL 24 h) ou que l'email se perdait, l'utilisateur restait
  « non vérifié » sans recours ;
- la page `/verifier-email?ok=0` (lien invalide) affichait « Créez un nouveau
  lien en vous inscrivant à nouveau » — ce qui est **trompeur** : un compte
  existe déjà avec cet email, donc une réinscription renvoie `409` (T-136) ;
- le champ `emailVerified` était récupéré dans Mon compte mais jamais affiché.

**Solution.**
- Nouvelle route `POST /api/auth/resend-verification` :
  - authentification requise (le destinataire est l'utilisateur courant —
    aucune adresse arbitraire, donc pas de vecteur d'abus/énumération) ;
  - rate-limit strict (5 / heure / utilisateur) ;
  - si l'email est déjà vérifié → message générique sans envoyer d'email ;
  - sinon émission d'un nouveau token `email_verification` (mécanisme existant
    `issueToken`, hash SHA-256 en base, TTL 24 h) et envoi best-effort ;
  - échec SMTP → `502` explicite (l'inscription reste best-effort également).
- Nouveau composant `src/components/resend-verification-button.tsx` : bannière
  + bouton « Renvoyer l'email » affichés uniquement si non vérifié, insérés en
  tête de l'onglet profil de `mon-compte/page.tsx`.
- Page `/verifier-email?ok=0` : texte corrigé (plus de « réinscrivez-vous »)
  et deux actions : « Se connecter » et « Mon compte » (où se trouve le
  renvoi).

**Sans régression :** le flux d'inscription et le lien de vérification
existant (`/api/auth/verify`) ne sont pas modifiés ; le nouveau token utilise
exactement le même mécanisme (consommation à usage unique).

**Preuve runtime (DEV), bout-en-bout :**
- compte tiers non vérifié → `POST resend-verification` → 200 « email envoyé » ;
- l'email en file (`emailOutbox`, statut `sent`) contient bien le lien
  `/api/auth/verify?token=…` ;
- suivi du lien → **307 `/verifier-email?ok=1`** (compte vérifié) ;
- 2ᵉ utilisation du même token → **307 `/verifier-email?ok=0`** (usage unique,
  `consumeToken` atomique) ;
- compte déjà vérifié → 200 « Votre email est déjà vérifié » (pas d'email) ;
- anonyme → **401**.

## Zones vérifiées et saines (pas d'anomalie retenue)

- **Recherche** (`/recherche`) : robuste aux entrées aberrantes (dates
  passées/invalides, `checkOut<checkIn`, prix négatifs, `minPrice>maxPrice`,
  `guests=0/9999/abc`, `page=99999/abc`, injection SQL) — toutes répondent 200
  avec des résultats cohérents (0 ou bon filtre). Filtres `city` (ilike,
  insensible casse), `type`, `amenity`, prix (normalisé EUR) fonctionnent. Le
  `country` en égalité stricte n'est pas exposé dans le formulaire (lien
  uniquement) → pas de bug visible.
- **Messagerie / pièces jointes** : création de conversation (hôte sans
  réservation → 400), upload avec vérification des magic bytes (faux PNG →
  400), anti-réutilisation de pièce jointe (400), contrôle d'accès strict :
  participant (voyageur/hôte/admin) → 200, tiers → 403 en lecture, écriture ET
  téléchargement ; anonyme → 401 ; message absent → 404.
- **Parrainage / Best-Rewards** : code généré à l'inscription, résolution non
  bloquante, récompense versée une seule fois (`referralRewardedAt`) au séjour
  terminé dans le cron, avec verrou ligne du parrain.
- **Wishlists / partage** : création, bascule publique/privée, rotation de
  token, suppression ; `/wishlists` n'est pas une page (les favoris sont sur
  `/mes-favoris`, le partage sur `/wishlists/share/[token]`) → le 404 est
  normal.
- **Alertes de prix** : création/mise à jour idempotente, opt-in notification,
  validation zod, propriété inexistante → 404.
- **Promotions** : simulation correcte (10 % → 180/200), code inconnu 404,
  montant invalide/négatif/0 → 400, montant minimum (`fixed` 20 € sur 10 €)
  → 400 en français.
- **2FA TOTP** : setup protégé par mot de passe, remplacement nécessitant le
  code actif, promotion atomique du secret pending, aucun secret vers un tiers.
- **Auth** : login/register/forgot/reset robustes (anti-énumération sur
  forgot → 200 générique), `next=` après connexion/inscription avec
  `safeNextPath` (anti-redirection ouverte), change-password révoque les
  autres sessions.
- **Avis** : éligibilité serveur (`isReviewEligible` : séjour terminé), un
  seul avis par réservation, propriété de la réponse (403 sinon).
- **Actions groupées admin** : garde admin, auto-exclusion de l'admin, audit
  log, FSM réservation respectée (annulation uniquement pending/confirmed).
- **Facture** : la facture client est disponible (`/api/bookings/[id]/invoice`,
  contrôle owner/hôte/admin) ; le pavé « Factures légales indisponibles » du
  billing hôte est une limitation assumée (moteur comptable), pas un bug.
