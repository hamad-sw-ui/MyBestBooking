## A1 — Libellé zod anglais sur `reset-password` (token trop court)

**Problème.** `POST /api/auth/reset-password` validait le jeton avec
`token: z.string().min(10)` **sans message explicite**. Un jeton mal formé
renvoyait donc, à l'exécution, le libellé zod anglais par défaut :

```
{"error":"Too small: expected string to have >=10 characters"}  HTTP 400
```

C'est le dernier reliquat des fuites i18n traitées en T-137/T-138 : les autres
routes d'authentification produisaient déjà des messages en français (vérifié
runtime : login → « Email invalide », 2FA verify → « Code TOTP à 6 chiffres
attendu », change-password → « Le mot de passe doit contenir au moins 8
caractères », register → messages personnalisés).

**Solution.**
- Message explicite : `token: z.string().min(10, "Lien de réinitialisation invalide")`.
- Le bloc `catch (z.ZodError)` utilise désormais `frenchZodMessage(error)`
  (cohérence avec le reste de l'API et filet de sécurité pour tout futur champ).

**Sans régression :** le statut reste 400 ; le comportement fonctionnel
(jeton valide → réinitialisation + révocation des sessions ; jeton
expiré/invalide → « Lien invalide ou expiré ») est inchangé.

**Preuve runtime (DEV + PROD).**
- token court → `400 "Lien de réinitialisation invalide"` (DEV + PROD 3100) ;
- flux complet légitime : `forgot-password` (200, email `sent` contenant
  `reinitialiser?token=…`) → `reset-password` avec le vrai jeton → `200
  « Mot de passe réinitialisé »` → connexion avec le **nouveau** MDP `200`,
  avec l'**ancien** MDP `401`, et **réutilisation** du même jeton → `400`
  (usage unique via `consumeToken`).

## Parcours bout-en-bout vérifiés et jugés sains

### Connexion 2FA TOTP
- setup avec mauvais mot de passe → `401 « Mot de passe incorrect »` ;
- setup correct → secret base32 renvoyé (secret pending, 2FA pas encore active) ;
- verify avec code faux → `400 « Code invalide »` ; verify avec TOTP valide
  (généré via `speakeasy`) → `200 {enabled:true}` ;
- login sans code → `401 {twoFactorRequired:true}` ; login avec code faux →
  `401 {twoFactorRequired:true}` ; login avec bon code → `200` + session
  authentifiée (`/api/auth/me` 200) ;
- disable avec MDP + code → `200`, 2FA revenue à `false` (compte démo
  restauré). L'écran de connexion gère bien `twoFactorRequired` (champ
  `totpCode` / `one-time-code`).

### Partage public de wishlist
- passage en public → `shareToken` émis ; page `/wishlists/share/<token>`
  accessible **anonymement** (200) et listant les favoris ;
- rotation de token → l'**ancien** jeton renvoie 404, le nouveau 200 ;
- retour en privé → le jeton renvoie 404 ; jeton invalide → API 404
  (« Introuvable »).

### Upload de photos d'hébergement (public)
- hôte : POST `/api/properties/upload` d'un PNG → `{url:"/uploads/<file>"}` ;
  le fichier est servi **publiquement** (anonyme, `200 image/png`) ;
- client (rôle customer) → `403 « Réservé aux hébergeurs »` ;
- fichier texte renommé `.png` → `400` (magic bytes, « Le fichier n'est pas
  une image valide… »).

### Achat invité (réservation sans compte)
- réservation anonyme `isGuestBooking:true` → `confirmed`/`paid`, profil invité
  créé **sans mot de passe** (`passwordHash=null`, `emailVerified=false`),
  emails « Réservation confirmée » + « Accédez à votre réservation » (ce
  dernier contenant le lien `/activer-compte` = claim) ;
- **garde anti-détournement** : un invité anonyme utilisant l'email d'un compte
  existant (`customer@…`) → `409 « Connectez-vous pour réserver avec cet
  email »` ;
- un invité ne peut pas consommer de wallet (`useWalletCredits:true` →
  `walletCreditsUsed:"0.00"`).

### Autres points vérifiés

- **Préférences** : PATCH langue/devise/`priceAlertEnabled` persisté et relu ;
