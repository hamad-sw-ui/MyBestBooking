## 2. Anomalie corrigée (P2 — validation API incohérente avec l'UI)

**Problème.** `POST /api/messages` validait `content` avec
`z.string().min(1).max(4000)`, ce qui accepte un message **constitué uniquement
d'espaces** (`"   "`, longueur ≥ 1) tant qu'aucune pièce jointe n'est requise.
Le composant client (`message-composer.tsx`) empêche déjà l'envoi d'un message
vide (et envoie `"(pièce jointe)"` quand il n'y a qu'un fichier), mais l'API
directe créait un message vide visible dans la conversation — incohérence et
résultat « mal pensé » (bulle de message blanche).

Preuve runtime (avant) : `POST /api/messages {content:"   "}` → **201** avec
`content:"   "` stocké.

**Solution (sans régression).** Dans `src/app/api/messages/route.ts`, après les
contrôles d'accès :
- normalisation `const trimmedContent = data.content.trim()` ;
- rejet **400 « Le message ne peut pas être vide »** si `!trimmedContent &&
  !attachmentKey` (un message avec pièce jointe seule reste autorisé) ;
- stockage de `trimmedContent || "(pièce jointe)"` (les espaces superflus sont
  aussi normalisés, sans impact sur les messages réels).

Aucun changement de contrat pour les messages valides ; le comportement du
composant client reste identique (il satisfait déjà la règle).

Preuves runtime (après, DEV + PROD) : message d'espaces → **400 « Le message ne
peut pas être vide »** ; message texte normal → **201** ; l'UI (pièce jointe
seule → `"(pièce jointe)"`) reste acceptée.
