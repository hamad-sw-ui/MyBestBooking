## A1 — Messages d'erreur zod en anglais sur des routes client/hôte non couvertes par T-137

**Problème.** T-137 avait introduit `frenchZodMessage()` et l'avait appliqué à
4 routes grand public (bookings, reviews, price-alerts). Restaient exposés en
anglais, à l'exécution, sur des routes utilisées par le client ET par l'hôte :

- `POST /api/messages` avec `content:""` → `400 "Too small: expected string to have >=1 characters"`
- `POST /api/conversations` avec `propertyId` mal formé → `400 "Invalid UUID"`
- `POST /api/reviews/[id]/reply` avec `reply:""` → `400 "Too small: expected string…"`
- `PUT /api/rooms/[id]/availability` avec `price:-5` → `400 "Too small: expected number to be >0"`
- ainsi que `wishlists`, `reviews/[id]/moderate`, `rooms`, `rooms/[id]`,
  `rooms/[id]/rate-plans`, `properties`, `properties/[id]`,
  `properties/[id]/validate`, `promotions`, `promotions/[id]`, `users/me`
  (toutes renvoyaient `error.issues[0].message` brut).

En parallèle, les schémas qui fournissent déjà un message explicite en français
(register « Le prénom doit contenir au moins 2 caractères », wishlists « Le nom
est requis », rooms « Le prix de base doit être strictement positif »)
s'affichaient correctement : le problème était bien limité aux contraintes sans
message.

**Solution.**
- `frenchZodMessage()` (src/lib/http.ts) enrichi :
  - **détection UUID par le champ** (`/(^|_)id$|Id$/` ou champ contenant « uuid »),
    en plus du texte du message — couvre « Invalid UUID » (`invalid_format` Zod
    v4 sur `propertyId`, `roomId`, `bookingId`…) → « Identifiant invalide » ;
  - un texte en `min(1)` vide → « Ce champ est requis » (plus parlant que
    « Texte trop court » pour un contenu de message / une réponse d'avis vide).
- Helper appliqué à toutes les routes à message exposé (import
  `frenchZodMessage`, remplacement de `error.issues[0].message` /
  `e.issues[0]?.message ?? "Payload invalide"`).
- Tests : +2 cas (UUID mal formé → « Identifiant invalide » ; texte vide →
  « Ce champ est requis »).
- Les routes d'authentification (register, login, 2FA, change-password,
  forgot/reset) n'ont **pas** été modifiées : leurs schémas portent déjà des
  messages personnalisés en français (vérifié à l'exécution).

**Sans régression :** le code de statut reste 400 ; les messages personnalisés
français sont préservés par `looksLikeDefaultZodEnglish()` (seuls les libellés
zod par défaut anglais sont traduits) ; aucun changement de comportement de
validation.

**Preuve runtime (DEV puis PROD `next start` 3100).**
- message vide → `400 "Ce champ est requis"` (DEV + PROD) ;
- `propertyId` mal formé → `400 "Identifiant invalide"` (DEV + PROD) ;
- disponibilité `price:-5` (hôte) → `400 "Valeur trop petite"` (DEV) ;
- réponse d'avis vide (hôte) → `400 "Ce champ est requis"` (DEV) ;
- réservation `numAdults:0` → `400 "Valeur trop petite"` (PROD) ;
- messages personnalisés intacts : `wishlists` name vide → « Le nom est
  requis », chambre prix 0 → « Le prix de base doit être strictement positif ».

## Zones vérifiées à l'exécution et jugées saines

- **Annulation / remboursement** (`booking-cancellation.ts` + route
  `cancellation`) : approche *persist-first* (DB marquée `cancelled` /
  `refund pending` avant l'appel PSP, reprise par le cron), frais calculés sur la
  politique *snapshotée* dans la réservation, part carte remboursée par le PSP
  (idempotent via `refundStatus`), crédits wallet et usage promo restitués via
  `releaseBookingBenefits` (garde `benefitsReleasedAt`, verrou ligne) ;
  contrôle owner/admin ; devis GET cohérent. Aucune anomalie.
- **Disponibilités** (`rooms/[id]/availability`) : upsert journalier, stock
  borné à la capacité de la chambre (`availableCount > quantity` → 400
  français), fenêtre GET ≤ 365 jours, ownership strict (client → 403). La
  saisie d'une date passée est acceptée mais sans effet métier (aucune réservation
  future ne la couvre) — non bloquant.
- **Plans tarifaires** (`rooms/[id]/rate-plans`) : ownership, validation
  enum politique, PATCH ciblé sur la bonne chambre ; pas d'endpoint DELETE (un
  plan se désactive via `isActive`) — comportement assumé.
- **Chambres / propriétés / promotions** : création réservée hôte/admin avec
  ownership (client → 401/403), prix strictement positif, quantité bornée,
  remise ≤ 100 %, plage de dates promo cohérente. Une propriété `draft`/
  `pending` est **invisible du public** : la fiche anonyme rend la page
  « Cette page n'existe pas » (soft-404 Next 16) avec `noindex` et **aucune
  donnée** de l'annonce (vérifié : nom absent), tandis que le propriétaire y
  accède (200) et peut la re-soumettre (T-137).
- **Suppression de compte** (`users/me` DELETE) : soft-delete RGPD (email hashé
  déterministe, prénom/nom/téléphone/2FA effacés, sessions révoquées, cookie
  supprimé), admin empêché de s'auto-supprimer ; le bouton est désactivé tant
  que « SUPPRIMER » n'est pas saisi.
- **Messagerie** : contrôle participant (tiers → 403, revérifié au n°15),
  content `min(1)`.
- **Tunnel de réservation** : accès direct sans `propertyId/roomId` → message
  explicite « Informations de réservation manquantes » + bouton retour (pas
  d'écran cassé).
- **Page d'aide** : recherche d'articles fonctionnelle, contact `mailto:`
  présent — aucun bouton mort.
- **Calendrier de disponibilité** (UI) : édition par ligne, batch PUT chunké à
  90 j, prix converti `Number(...)` ou `null` (cohérent avec l'API), stop-sell,
  pagination 90 jours, feedback succès/erreur.
- **Aucun handler mort** : recherche globale `onClick={() => {}}`, `href="#"`,
  `alert(`, `console.log` dans les composants → aucun résultat.
