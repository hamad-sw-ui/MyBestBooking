## 1. Analyse allégée (§14 — Q1, Q6, Q8)

- **Q1 — Impact** : seuls les e-mails sont modifiés. `newMessage` gagne un
  paramètre optionnel `url` (aucun appelant cassé : template backward
  compatible, testé sans url). `bookingHostCancellation` est un **nouvel**
  événement (aucun comportement existant modifié). La route `POST
  /api/messages` ne change pas son contrat HTTP (201, mêmes erreurs) ;
  l'appel de notification reste dans le `try/catch` best-effort.
- **Q6 — Régression** : le bloc admin `emailTemplates.newMessage` reste
  source de vérité **si personnalisé** (détection par comparaison aux
  DEFAULTS) → l'édition admin existante continue de fonctionner (testé).
  Le corps FR par défaut reste sémantiquement identique. Aucune table,
  aucune migration, aucun endpoint public modifié.
- **Q8 — Sécurité** : aucun secret exposé ; les nouvelles variables
  (`senderName`, `guestName`, `reason`, URLs) passent par `escapeHtml` /
  `renderTemplate` (testes anti-XSS ajoutés). Les URLs de CTA sont
  construites côté serveur avec `NEXT_PUBLIC_APP_URL` (aucune entrée
  utilisateur dans un href non échappé).

## 2. Implémentation

### 2.1 `newMessage` — CTA + localisation fr/en (`src/lib/mail/templates.ts`)
- Nouveau paramètre `url` (+ `senderName`, `firstName` échappés) ;
- Sujet/corps **plateforme localisés** (`strings.ts`) quand le bloc admin
  n'est pas personnalisé ; bouton « Répondre au message / Reply to the
  message » pointe vers la conversation ;
- Surcharge admin **préservée** (comparaison aux DEFAULTS) : si l'admin a
  rédigé son bloc, sa rédaction s'affiche telle quelle (compromis T-025),
  le CTA plateforme reste ajouté.

### 2.2 Route messages (`src/app/api/messages/route.ts`)
- URL ciblée selon le **rôle du destinataire** :
  - voyageur reçoit → `/messages/{conversationId}` ;
  - hôte reçoit → `/dashboard/messages/{conversationId}` ;
- Toujours la langue du destinataire (`users.language`) — déjà en place,
  conservée.

### 2.3 Nouvel e-mail d'annulation à l'hôte (`bookingHostCancellation`)
- Template **entièrement géré par la plateforme** (jamais édité par
  l'admin) → localisé fr/en dans la langue du **hôte** (approche
  `priceAlert`) : tableau (référence, hébergement, voyageur, dates), motif,
  CTA « Voir mes réservations / View my bookings » + lien dashboard ;
- Câblé dans `notifyBookingCancellation` (`src/lib/booking-cancellation.ts`)
  via l'outbox, eventKey déterministe
  `booking-cancellation:{id}:host` (aucun doublon possible), best-effort
  (un échec mail ne casse jamais l'annulation ni l'e-mail voyageur) ;
- L'e-mail voyageur existant (`booking-cancellation:{id}`) est inchangé.

### 2.4 Métadonnées admin
- `settings.ts` : placeholder `{url}` documenté pour `newMessage` ;
- `settings-panel.tsx` : variables affichées `{firstName}, {senderName},
  {url}` (aucun nouveau template dans le panneau — le contenu admin de
  `newMessage` reste le seul bloc éditable ; `bookingHostCancellation` est
  plateforme).

## 4. Limites connues (honnêtes)

- L'e-mail de **vérification à l'inscription** reste en français par défaut :
  le schéma `POST /api/auth/register` n'accepte pas `language` (le champ
  arrive ensuite via `PATCH /api/users/me`). Comportement **préexistant**,
  hors périmètre « messaging hôtes ↔ clients » — à traiter séparément si
  souhaité.
- Les corps édités par l'admin (`emailTemplates.newMessage`) gardent la
  langue de rédaction admin (compromis T-025) ; la localisation s'applique
  par défaut et au CTA.
- `bookingCancellation` (voyageur) et les autres blocs admin restent non
  traduits automatiquement (limite T-149 documentée, inchangée).
