## Méthode de détection de C1 (migrations divergentes)

Comparaison manuelle, table par table, entre :
- le SQL des `Migration` dans `AppDatabase.kt` ;
- les champs déclarés dans `entity/*.kt`.

Six divergences confirmées. Exemple le plus net, `sessions` :

```sql
-- MIGRATION_24_25
CREATE TABLE `sessions` (..., `staffName` TEXT NOT NULL, `startCash` DOUBLE NOT NULL,
  `expectedEndCash` DOUBLE, `actualEndCash` DOUBLE, `status` TEXT NOT NULL, ...)
```
```kotlin
// SessionEntity
val sellerName: String
val openingBalance: Double
val closingBalance: Double?
val expectedBalance: Double?
val totalCashSales: Double
val totalMomoSales: Double
val totalExpenses: Double
val isActive: Boolean
```

Aucun nom en commun au-delà de `id`, `startTime`, `endTime`.
De plus, la migration déclare `staffId` NOT NULL avec clé étrangère, l'entité le
déclare nullable et sans FK.

**Vérification croisée** : `exportSchema = false` → aucun schéma JSON de
référence n'existe dans le dépôt, ce qui explique que la divergence n'ait
jamais été détectée automatiquement. C'est la cause racine organisationnelle.

## Découverte annexe

`app/src/main/java/com/reconsiliation/caisse/conversation.txt` : 1 084 lignes de
transcription d'une session avec un autre outil de génération de code (« Rork »),
référant un package `com.rork.momocaisse` et une arborescence
`android/app/src/main/java/com/rork/momocaisse/`.

→ Le projet a probablement été initié par génération automatique puis renommé.
Cela éclaire plusieurs incohérences (migrations écrites de mémoire, code mort,
doublon `NotificationHelper`, versions Kotlin mélangées dans `.kotlin/errors/`).

Le fichier n'a **pas** été supprimé : la phase 1 était en lecture seule.
→ Tâche B-007.
