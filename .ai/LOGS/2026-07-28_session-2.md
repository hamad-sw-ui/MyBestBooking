## Découverte n°1 — `BackupManager` n'est branché nulle part

```bash
grep -rn "BackupManager\|exportBackupWithPassword\|importBackup" app/src/main \
  | grep -v "utils/BackupManager.kt"
# → AUCUN RÉSULTAT
```

Le meilleur code de sécurité du dépôt (PBKDF2 100 000 itérations, AES-GCM,
checksum, contrôle de robustesse du mot de passe, format ZIP avec métadonnées)
n'est **appelé par personne**. Les chemins réels restent
`MainRepository.backupDatabase` / `syncToCloud`, qui font un `transferFrom` brut.

→ **BUG-017** créé. C'est typiquement le défaut qu'un audit fichier-par-fichier
ne détecte pas : le fichier est excellent, c'est son absence d'usage qui pose
problème.

## Découverte n°2 — conflit `staff.pinSalt`

```
AppDatabase.kt:71  CREATE TABLE staff (... pinSalt TEXT NOT NULL ...)
StaffEntity.kt     val pinSalt: String? = null          ← nullable
```

Or la migration paresseuse des PIN (correctif n°5) repose sur `pinSalt == null`
pour détecter un hash legacy à re-hacher. La contrainte `NOT NULL` de la
migration entre en conflit direct avec ce mécanisme. À préserver lors de la
correction de BUG-001.

## BUG-001 : re-vérifié, maintenu

L'audit antérieur annonce une « vérification complète de la chaîne v18→v27 ».
Deux réserves factuelles :
1. La base est en **v28** (`MIGRATION_27_28` existe).
2. Les divergences migration ⇄ entité **subsistent**, vérifiées ligne à ligne :
   `AppDatabase.kt` lignes 71, 99, 113, 120, 127.

Hypothèse : l'audit antérieur a vérifié que la *chaîne* était **continue**
(aucun trou entre 18 et 27), ce qui est exact — mais pas que chaque migration
produisait un schéma **conforme aux entités**, ce qui est un contrôle différent
et que seul `exportSchema = true` + `MigrationTestHelper` peuvent garantir.
