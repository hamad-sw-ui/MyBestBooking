# Session 3 du 2026-07-28 — Phase 6 : environnement Docker

## Analyse préalable (avant d'écrire une ligne)

```bash
cat gradle/gradle-daemon-jvm.properties   # → toolchainVersion=21   ⚠️ DÉCISIF
grep distributionUrl gradle/wrapper/...   # → gradle-9.5.0-bin.zip
grep compileSdk app/build.gradle.kts      # → 35 ; jvmTarget = 11
grep -rn "detekt|ktlint|jacoco" build.gradle.kts app/build.gradle.kts libs.versions.toml
                                          # → AUCUN plugin qualité
which docker java                         # → command not found (les deux)
nproc; free -h                            # → 2 cœurs, 3.8 Go
```

### Le piège évité
`toolchainVersion=21` **et** `jvmTarget = 11` coexistent. On pourrait croire
qu'un JDK 17 (voire 11) suffit : faux. Gradle refuse de démarrer son daemon sans
le JDK exact demandé par le toolchain. Une image JDK 17 aurait échoué au premier
`gradlew`. → image **Temurin 21**.

### L'argument qui a tranché en faveur de Docker
`.kotlin/errors/*.log` (7 fichiers versionnés) mentionne les versions Kotlin
**2.0.21** puis **2.2.10**, alors que `libs.versions.toml` déclare **2.1.0**.
Le projet a donc été compilé depuis au moins trois environnements différents.
C'est exactement la classe de problème que Docker élimine — argument factuel
tiré du dépôt, pas une justification théorique.

## Décisions de conception et leur motif

| Décision | Motif |
|---|---|
| Contexte de build = `docker/` seul | L'image ne contient pas le code ⇒ jamais de reconstruction à chaque modification |
| Gradle **non** installé dans l'image | Le wrapper télécharge 9.5.0 : installer un Gradle système recréerait la divergence à éliminer |
| Kotlin **non** installé en binaire | Fourni par le plugin Gradle 2.1.0 ; un `kotlinc` système pourrait diverger |
| `sh ./gradlew` partout | `gradlew` non exécutable (B-001) et monté depuis l'hôte : on ne le modifie pas |
| `kotlin.compiler.execution.strategy=in-process` | Neutralise les échecs de daemon Kotlin vus dans `.kotlin/errors/` |
| `configuration-cache=false` en profil test | Contourne B-006 (instable avec Gradle 9.5 + KSP) |
| daemon activé en dev, désactivé en test | Vitesse d'itération vs. isolation stricte |
| sandbox en `:ro` + tmpfs | Rend structurellement impossible la pollution du dépôt |
| `USER_UID`/`USER_GID` | Évite les `build/` en `root:root` sur hôte Linux |

## Ce que je n'ai PAS fait, et pourquoi

- **Aucun émulateur dans l'image.** `SecurityMigrationTest` valide SQLCipher +
  AndroidKeyStore, adossé au matériel. Un émulateur conteneurisé donnerait un
  faux vert sur un test de sécurité — pire que pas de test. La Phase 6 l'exclut
  d'ailleurs explicitement.
- **Aucun plugin Gradle ajouté** (ktlint/detekt/jacoco). Modifier
  `app/build.gradle.kts` sortait du périmètre « créer l'environnement » et
  aurait mélangé deux chantiers. ktlint/detekt sont fournis en CLI autonomes ;
  les plugins sont tracés en B-135/B-136.
- **Aucune couverture inventée.** Sans plugin JaCoCo, la collecte est
  impossible : le rapport le dit au lieu d'afficher un chiffre faux.
